# LEDs: initialization, resources, and SMC transport

Source review and candidate correction of `drivers/leds/leds-xenon.c` from `techflashYT/linux-custom@a293dd19311668900eb1eeb2f6cb01dcac54f330`. No hardware test was performed in this experiment.

## Established defects and scope

- `xenon_led_init` returns an uninitialized `ret` on its success path, reported by LLVM 16 during E26. However, installed-binary disassembly shows `li r31,0` and a return of that value. Do not claim that this binary returns a random value; the source undefined behavior still needs removal.
- `module_platform_driver` appears alongside `module_init` and `module_exit`, although this kernel's headers define them as alternative mechanisms. The built-in System.map contains two initialization functions. As a module, the macros define duplicate entry points; separate compilation tests the incompatibility.
- The created device pointer is not retained, and the original exit path does not unregister that device.
- LED-name allocation failures are unchecked. If, for example, the third LED registration fails, the original returns without removing the first two or freeing their names. This is error-path analysis, not induced console memory exhaustion.
- `xenon_led_set` releases its state lock before sending. Concurrent callers can therefore send states in reverse order. No physical interleaving was reproduced.

## Concrete SMC-cache caller

The driver builds a 16-byte command with ID `0x99` and calls `xenon_smc_message_wait`. Installed disassembly confirms the call after unlocking. The high bit of 0x99 causes `_xenon_smc_wait` to return immediately, but `xenon_smc_message_wait` subsequently searches the cache anyway. 0x99 is absent from the thirteen cached IDs.

This is a concrete caller of E25's unbounded search during LED initialization and updates. It strengthens the reachability analysis but does not measure effects on live memory or establish causality with E10.

## Candidate patch 0005

The driver now has one init/exit pair, explicitly registers the driver then device, removes them in reverse order, and returns zero on success. LED instances, names, and registrations use checked device-managed resources. Release ordering retains names and structures until LED unregister completes.

Sending uses `xenon_smc_message`, without reply-cache lookup, while holding the state lock to preserve send order. In the inspected source, this send takes the FIFO lock and does not sleep; no reverse FIFO-to-LED lock path was identified in these functions. The SMC core's unbounded FIFO-ready loop remains unresolved by this patch.

Resource-contract references: [devres](https://docs.kernel.org/driver-api/driver-model/devres.html), [LED class](https://docs.kernel.org/leds/leds-class.html), and the exact `drivers/leds/led-class.c` / `drivers/base/dd.c` implementations in the pinned revision.

## Off-console verification

`research/tests/check-led-lifecycle.py` compiles the actual candidate after replacing headers with resource/FIFO mocks. ASan/UBSan are enabled and warnings are errors.

Twenty-one cases cover success/removal, driver-registration failure, device-creation failure, unavailable SMC, nine allocation failure points, and eight LED-registration failures. They check returned errors, no retained resources, valid names throughout removal, and all eight command bits. The mocked FIFO verifies sending under lock. Real IRQs, SMP scheduling, and visual behavior are not simulated.

PowerPC module compilation of the original reproduces four init/exit redefinitions. After patch 0005, C compilation passes but modpost fails because `xenon_smc_ready` is not exported. Patch 0006 adds its GPL export; the separate module then builds fully without diagnostics. Both failures and the final success are preserved. The SMC core is included by CONFIG_PPC_XENON; CONFIG_XENON_SMC selects only its character interface and is not a dependency to add to the LED driver.

Evidence: `evidence/2026-10-01/led-audit/`. The final integrated checkpoint was **6.18.11-xenon-obsidian3**, with results in `kernel-build-obsidian3/`; intermediate obsidian2 is retained separately. No Xbox installation occurred within this experiment; later booted descendants are tracked in STATE.
