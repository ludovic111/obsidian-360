# SMC: Linux protocol and reply-cache bounds

Off-console analysis dated October 1, 2026. No unknown SMC message was sent and no hardware access was added during this experiment.

## Source and evidence chain

Source: `techflashYT/linux-custom@a293dd19311668900eb1eeb2f6cb01dcac54f330`, `drivers/xenon/smc-core.c`, SHA-256 `87bb7876e93f2896b1694e44d29d22af36270751c12eed9815572985918215d7`. The complete archive matched the ArchPOWER recipe's hash, `b3e0b3a92523f334e594e07b57da58e459b4d21630ec1366aba48297da9282f0`.

The installed binary identified in E20 contains the same unbounded `_xenon_smc_cached_reply` loop: `lbzu r9,16(r10)` advances one entry, and exit depends on a zero byte or matching ID without an array-end comparison. See `evidence/2026-10-01/smc-audit/_xenon_smc_cached_reply.asm` and `cache-binary-check.json`.

## Cache defect

`smc_reply` has thirteen 16-byte entries with IDs `01 04 07 0a 0f 11 12 13 16 17 1e 20 83`. No zero sentinel terminates the array. The original search nevertheless expects one and reads beyond the allocated 208 bytes for an absent ID.

`research/tests/check-smc-cache.py` extracts the actual table/function and compiles them with AddressSanitizer. All thirteen known IDs pass. Scanning all 256 possible values produces an original `global-buffer-overflow`; the ARRAY_SIZE-bounded candidate completes with exactly thirteen matches. Four cases verify their expected outcomes. Evidence: `smc-audit/cache-bounds.json`.

Patch `0004-xenon-bound-smc-reply-cache.patch` bounds only this search. It does not resolve the other protocol limits or establish E10's cause. The source defect and presence in installed code are confirmed; triggering it on hardware was not attempted.

## Transport and concurrency: source analysis

| Component | Observed source behavior | Limit |
|---|---|---|
| Send | 16-byte message; four words through FIFO offset 0x80, control 0x84 | Unbounded ready wait under lock with local interrupts disabled |
| Receive | FIFO 0x90, control 0x94, response copied into cache | Global shared cache; no transaction identifier |
| Wait | Messages with bit 0x80 do not wait; others wait for `smc.cmd == msg[0]` | No maximum delay; wait_event_interruptible result ignored |
| Synchronization | Lock surrounds each FIFO transfer | No mutex covers the complete send/wait/read transaction |
| Interrupt | Status 0x50, acknowledgement 0x58, cache update and wake | Handler returns IRQ_NONE even after receipt; impact needs analysis |
| Userspace | `/dev/smc` requires 16-byte messages and a single opener | This does not serialize internal ANA, clock, and temperature consumers |

Stale or interleaved replies are risks inferred from these paths, not reproduced incidents. No physical-SMC concurrency test was performed. ANA reading does not explicitly validate a reply status before decoding data bytes, limiting the interpretation of earlier captures.
